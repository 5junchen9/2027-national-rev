依据：[官方规则PDF](https://www.worldrobotconference.com/static/upload/file/20251031/1761890277382065.pdf)，检查了顺序、场地图、时间表、搬运和舞蹈说明。

- 五项顺序及8分钟总限需要满足；每项从起始线进入、区域间自主完成。当前按路标和固定步数运行，未证明始终在规定路线或起始线位置。
- 搬运按指定物块实际到指定位置计分；“二维码附近”是当前实现目标的描述，不能替代裁判要求的放置区域。
- 足球按实际踢球/进球评分。现有行走带球远离检测不证明射门得分；按用户此前约定保留。
- 舞蹈须到对应区域、扫码、音乐和动作完成。蓝地覆盖判据不能证明双脚或整机进区。
- 当前停止逻辑不是硬件急停；同步DZZ动作发送后不可由Q立即撤回。

## 6. 成熟开源方案与适用边界

本次核对原项目说明及源码，未克隆、安装或部署第三方项目。

1. [AprilRobotics/apriltag](https://github.com/AprilRobotics/apriltag#pose-estimation)：使用真实标记尺寸、fx/fy/cx/cy估计位姿，也明确提到OpenCV IPPE_SQUARE。说明7cm尺寸只是输入的一部分，不能代替相机标定。AprilTag不是普通二维码，不将它直接替换赛事指定二维码。
2. [Duckietown/lib-dt-apriltags](https://github.com/duckietown/lib-dt-apriltags)：Python封装同样要求camera_params及tag_size，返回角点、位置和估计误差。可借鉴测量输入/输出与误差检查，不是当前二维码的直接解码替代品。
3. [Nav2停靠实现](https://github.com/ros-navigation/navigation2/blob/main/nav2_docking/opennav_docking/src/simple_charging_dock.cpp)：拒绝超时检测，过滤检测位置，并在检测标记位置上加入最终停靠位置偏移。这一点最贴合“把物块放在二维码附近”：二维码中心、相机、机器人和物块落点是不同位置。
4. [PhotonVision单标记三维跟踪](https://github.com/PhotonVision/photonvision/blob/main/docs/source/docs/apriltag-pipelines/3D-tracking.md)：单个平面方形标记可能存在两个位姿解，应检查误差和时间连续性，不能看到一个PnP结果就直接相信。
5. [OpenCV solvePnP官方说明](https://docs.opencv.org/4.x/d5/d1f/calib3d_solvePnP.html)：四角点必须与真实方形点顺序对应；输出是目标相对相机的旋转与平移。二维码外接矩形的角不是斜拍二维码的真实角，不可直接代用。

建议按现有平台保留zbar精确内容匹配，再获取同一个目标二维码的四个真实角点；7cm需对应所取角点之间的实体边长，而非含白边的纸张边长。相机原始图、翻转后图、分辨率和内参坐标应一致；当前USB有安装翻转，测距前必须明确坐标变换。先在预览中验证三个实测距离，再接身体动作。

用户要求“附近即可”时可先用实际放置位置的二维码尺度参考，不输出伪厘米；斜角变化会影响宽度，因此仅适合近似正对、固定头位、固定立牌的条件。要稳定应对倾斜，应采用四角点PnP。两条都还没有新增进当前代码，不把已有D下沿判断当成已实现。

实施顺序建议：姓名标签范围与误播报 → 负载右转稳定 → 实测投放位置判据 → 路线角度/距离 → 8分钟整场。暂不加入ROS2/Nav2框架、SLAM或自动无限重试。
