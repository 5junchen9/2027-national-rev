# 只跟球与头部保持

## 部署

将以下三个文件一起覆盖到树莓派 `/home/yuting/robot_env/app/`：

- ball_debug.py
- handover_debug.py
- walk_kick.py

沿用当前启动命令，不覆盖config，初始头位仍129。修改前Git标签 `backup-before-remove-goal-20261005` 指向 `c1aa98a`。

## 当前行为

当前 `main.py handover --run --actions` 不再调用GoalTracker，不画球门框，也不等待球门稳定或向球门转弯。根据当前控制相机中的球框横向对齐，居中后执行一步UP_LITTLE，再重新观察。无单独踢球动作。旧球门模块留存供其他旧入口使用。

任一相机有合格球框时，不再发新的头部追踪或搜索移动指令，不要求球框位置已经稳定。腹部交接只切换控制相机，保持当前头位，不回正。若腹部丢失但头部仍有球，回到头部控制；两边都丢失时才启动原多轮上下搜索。身体仍要求稳定观察确认，最多30次身体动作。

头部已在执行的舵机小步会先完成，不保证在识别瞬间机械停止。舵机没有位置反馈，初始头位与手动G重启仍是明确的头部指令。程序不通过关闭PWM来强行停止，避免失去保持力。

球候选增加与紧邻外圈的亮度、饱和度或色相差异检查：亮度差至少20、饱和度差至少25或色相差至少10（OpenCV HSV单位），通过其中一项才继续。目标是排除与周围属于同一块地面的区域；这不是身份识别，强阴影或亮斑仍可能误检，外观非常接近背景的球也可能漏检。保留上一版圆弧、亮球面和旧框恢复逻辑。

## 验证

140项本地检查通过，覆盖有球但未稳定时没有头部搜索指令、腹部接管保持搜索后头位、无球门检测时仅根据球行走、无搜索身体转向，以及低对比绿色地面斑块拒绝。摄像头、串口和GPIO使用测试替身，真实识别率、机械停稳和树莓派处理帧率尚未验证。
