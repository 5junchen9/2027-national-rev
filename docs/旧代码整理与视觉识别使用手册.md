## 2 本轮整理与修复

应用逻辑集中在app，硬件逻辑集中在hardware，模型和资源集中在assets。所有路径从项目根自动定位，外部环境变量优先于config文件；配置按数据解析，不执行shell。来源映射见`docs/source_manifest.json`，记录原文件、SHA256和迁移位置。

沿用已完成的离线中文女声、WM8960具名播放、原录音优先、串口连接复用及异常释放。保留115200 8N1、25对FA请求、24槽FD在线动作格式，保留18份DZZ、通用动作倍率1.5、直行倍率2.5、动作间隔0.8秒、大转弯7次和头部95/120度。舞蹈第2段文件保留，默认流程仍只执行1/3/4/5段。

本轮补齐三处维护需要：主相机恢复USB默认；人脸置信度和确认次数放入配置，默认仍为0.65和2次；读取失败或人脸消失后清空连续确认计数。最后一项避免不同观察片段拼成一次“连续确认”，但没有证明模型本身的准确率提升。

直接文字/图片路线发送动作无需打开摄像头；相机扫码仍使用原相机。增加只读模型诊断入口vision，保留全部类别分数、模型元信息、前两类分数差与单图分类耗时。它不打开相机、串口或GPIO，不会触发伤心后的舞蹈。

将整理版文件夹复制到`/home/yuting/robot_legacy`后执行：

```bash

source venv/bin/activate

```

也可将交付的raspberry_pi_legacy_clean.zip上传至/home/yuting，压缩包内部顶层目录为robot_legacy。首次解压执行下列指令，再运行上面的安装与检查。若已有同名robot_legacy目录，先保留旧副本，避免混入旧配置。

```bash
cd /home/yuting
unzip raspberry_pi_legacy_clean.zip
cd /home/yuting/robot_legacy
```

setup要求64位Raspberry Pi OS arm64，因为原人脸和表情EIM是AArch64可执行模型。依赖通过apt和本地venv安装；venv继承系统包。setup不修改boot配置、不创建服务、不自动执行动作。本轮未在树莓派运行apt安装，现有驱动以现场为准。

### 3.1 串口路径

```bash
ls -l /dev/serial/by-path/
```

列表右侧`../../ttyUSB0`是相对于链接所在目录的目标。配置应使用`/dev/ttyUSB0`或左侧完整`/dev/serial/by-path/...`，不能填写`ttyUSB0`、`0`或`../../ttyUSB0`。两条别名若都指向ttyUSB0，仍只有一个设备。

机器人控制板与语音模块必须确认是不同的物理端口。机器人115200、语音模块9600。编辑config中的`ROBOT_SERIAL_PORT`和`VOICE_SERIAL_PORT`，或仅在本次会话临时覆盖：

```bash
export ROBOT_SERIAL_PORT=/dev/ttyUSB0
```

上例仅在接线确认ttyUSB0是机器人板后使用。语音模块尚未接好时先测独立任务，不运行语音总控。

### 3.2 原USB相机

```bash
v4l2-ctl --list-devices
ls -l /dev/v4l/by-path/
```

ROBOT_CAMERA_DEVICE填写原USB的实际视频节点，优先by-path路径。之前日志为video0/video1，两个节点不能当作两只摄像头；其中需选可取图节点。ROBOT_CAMERA_BACKEND固定使用usb作为原任务输入，ROBOT_CAMERA_FLIP默认0即上下翻转，按实测方向调整none、0、1或-1。

CSI采集适配代码作为已有参考保留，安装脚本不额外安装Picamera2，本轮不接入原任务。不要通过把全局backend改成csi来实现辅助融合，那会把旧任务的输入也换掉。后续需独立角色接口，二维码解码器只接原USB。

### 3.3 音频与配置项

```bash
aplay -l
arecord -l
python3 main.py mic --list-devices
```

确认WM8960播放和录音设备。ROBOT_AUDIO_CARD按名称wm8960soundcard选择，避免卡编号变化后播放到HDMI；ROBOT_MIC_DEVICE按输入列表索引填写。总控初始化会复用原WM8960混音设置。独立听音若音量仍低，先核对实际混音状态，再调整ROBOT_SPEAKER_VOLUME，范围0至127，默认120。

| 参数 | 默认 | 用途 |
| --- | --- | --- |
| ROBOT_CAMERA_BACKEND | usb | 原任务相机类型 |
| ROBOT_CAMERA_DEVICE | 0 | 待现场确认的原USB节点 |
| ROBOT_FACE_CONFIDENCE | 0.65 | 原五人分类接受阈值 |
| ROBOT_FACE_CONFIRM_FRAMES | 2 | 同一标签连续确认次数 |
| ROBOT_EMOTION_CONFIDENCE | 0.52 | happy接受阈值 |
| ROBOT_SAD_CONFIDENCE | 0.95 | sad接受阈值 |
| ROBOT_TTS_SPEED | 150 | 中文女声语速 |

阈值是业务判定规则，不是识别准确率。提高sad阈值可能降低误触发，也可能让伤心类一直未识别；降低阈值会增加接受数量，不能据此宣称更准。应在独立验证集上选择阈值。

## 4 原功能测试与命令

统一入口不加任务时只检查。--run表示允许相机、GPIO或身体等真实任务，旧根目录脚本的参数不能直接套用到整理版。

### 4.1 不运动的检查

```bash
python3 main.py check
python3 main.py simulate
python3 main.py protocol check
python3 main.py qr --source F2,L90,F1,R90,F2
python3 main.py carry
python3 main.py kick
```

预期软件测试OK、197帧有效、模拟调用顺序正确；QR预览应为UPx2、TURN_LEFTx7、UPx1、TURN_RIGHTx7、UPx2。模拟人脸结果是占位值，不是模型识别率。

### 4.2 原USB相机与扫码

```bash
python3 main.py camera --run
python3 main.py qr --run --dry-run
```

先遮住原USB镜头确认画面来源和方向，Q或ESC退出预览；再放原路线码，确认解码内容和路线顺序。扫码dry-run只扫描和解析，不发送动作。图片URL需要网络取得原图，路线标注写入项目根qr_route_preview.png。

### 4.3 基础动作

```bash
python3 main.py protocol --run probe
python3 main.py action --run
```

probe应读回24槽位置。action启动即发送站姿，在action提示符逐条输入STAND、UP_LITTLE、BACK、TURN_LEFT、TURN_RIGHT，完成后QUIT。UP_LITTLE目前和UP共用前进DZZ，并非真正缩短的步长。留出活动空间，上一条站稳再执行下一条。Ctrl+C退出程序不等于控制板具有已验证的硬件急停。

基础动作通过后，短路线真实前进用：

```bash
python3 main.py qr --run --source F1
```

此命令不需要相机。原USB扫码后真实执行路线用`python3 main.py qr --run`，先确认路线长度和转弯标定，不以长路线作为第一次动作测试。

## 5 现有人脸和表情识别链路

原USB取得BGR图像，经方向处理；Haar先定位人脸，截取人脸区域；FaceClassifier转RGB并按EIM中的Studio设置缩放；模型输出标签分数；任务根据阈值和连续帧判定，随后播报或动作。

人脸任务取最大人脸框，五人标签为haowenwan、wujuncheng、xieyuting、yangchengrui、zhaobowen。它属于有限类别的图像分类，当前程序没有验证过的陌生人拒识机制；未知面孔也可能给某个已知类别高分。模型本身是否有其他标签需导出元信息确认，不能仅凭代码推断训练集。

表情任务取最大人脸，四周留15%余量并裁成正方形，只有happy和sad标签进入业务，其余都为unknown。默认6秒一轮，最多2轮，连续3次确认。它识别可见表情，不等同于可靠判断真实心理情绪；交互输出应保留未知和询问，不把预测当事实。

当前BGR转RGB符合Edge Impulse官方SDK。用户已确认训练时使用整张照片，而当前程序先裁人脸再分类，两边输入不一致。模型可能利用背景、人物位置或衣服特征；这些是否是主要错误来源，还要通过同图整图与裁脸对照确认。人脸检测、输入裁剪、模型分类和阈值判定应分别测，不能只看最终播报。

## 6 怎样优化Edge Impulse

### 6.1 先让输入与训练一致

观察原USB图像是否翻转、模糊、曝光过强，打印图片是否反光，脸是否足够大。记录Haar漏检与分类错判分别发生多少次。当前已确认训练整图、上线裁脸，应重新制作与实际裁剪一致的训练样本；若增加对齐，训练和上线同时采用相同流程。先校验Haar框是否包含完整眼睛和嘴巴，再考虑换YuNet；裁错的人脸无法靠调分类阈值补救。不要无依据地改RGB或给所有图强行美化。

对同一原始样本，保存上线实际送入模型的人脸裁剪，在Studio测试和树莓派导出EIM分别测。检查输入宽高、RGB/灰度、缩放模式和标签；比较float32与量化版本是否明显不同。官方指南列出的常见原因包括数据不足、现场输入分布不同、过拟合、类别不均衡和量化损失。

执行顺序建议：先修testing等错误标签及happy/sad定义；再统一裁剪；按人员或拍摄批次重新拆分数据；重新训练并导出float版本；最后用同一现场测试集比较原模型和新模型。历史float错误已经出现，改平台或继续调0.52、0.95不会自动补回缺失特征。收集每个稳定认错的例子作为失败分析样本，但最终独立测试集另行保留。

### 6.2 补齐有代表性的样本

人脸每位已知对象采集多个独立拍摄批次，覆盖正脸、轻微左右侧、不同距离、不同背景和现场打印/显示条件；另加入其他人或未知打印脸作为拒识评估。表情包含不同人的happy、sad、neutral/other，避免同一人只出现在一个类别、模型学到身份而非表情。模糊到无法判断的样本应标记质量不足，不随意贴happy或sad。

可先以每类100至300张有差异的训练样本、每类至少30张独立测试样本作为采集起点；这是工程建议，不是保证准确率的数量。连拍几百张近乎相同帧不算足够多样。真人拍摄与AI合成打印脸分布不同，新规图片需要独立验证。

按拍摄批次分训练/验证/测试，表情还应按人员隔离，防止相邻视频帧泄漏到测试集；五人身份训练与测试包含同五人，但测试必须来自不同拍摄条件。先用验证集调模型和阈值，最后测试集只用于最终评估，不能反复拿同一测试集调参。

### 6.3 衡量真正改善

输出完整类别分数与混淆表，统计每类召回、精确率、未知误接受率、拒识率和模型耗时。总准确率不能掩盖“多数happy很好、sad几乎全漏”。比较最优和次优分数差，验证是否能帮助拒绝模糊样本；分数不是校准后的正确概率。

保留当前阈值作为基线，用独立验证集选择每类阈值。连续确认或短窗口投票只能减少抖动，不能修复稳定的系统性错判；相邻帧高度相似，增加确认次数并不等于独立证据增多。对长期不确定结果设置退出，不强行跳舞或报人名。

## 7 无动作模型诊断

仅查看模型输入、标签和元信息：

```bash
python3 main.py vision --model face --output face-info.json
python3 main.py vision --model emotion --output emotion-info.json
```

需要在树莓派执行，因为原EIM是Linux arm64程序。工具只加载模型，不打开摄像头、串口或GPIO；JSON已用ASCII转义输出，终端不能输入中文也可使用。输出文件若存在会拒绝覆盖，换新名字即可。

将与上线裁剪一致的单张人脸文件保存为sample.png，再测试：

```bash
python3 main.py vision --model face --image sample.png --output face-sample.json
python3 main.py vision --model emotion --image sample.png --output emotion-sample.json
```

工具不自动做人脸检测或裁剪，因此整张场景照片不是等价输入。其报告包含原始最高分、全部分数、前两类差值、按现有阈值判定的task_label和分类耗时，不包含Haar检出率、连续帧行为或音频动作耗时。

独立测试集按“真实业务标签/图片”排列。人脸标签用上面五个英文类名及unknown；表情业务标签用happy、sad、unknown，其中unknown可放中性和其他不应触发交互的脸。每个标签下直接放图片，不使用更深的目录：

```text
evaluation/face/test/xieyuting/001.png
evaluation/face/test/unknown/001.png
evaluation/emotion/test/happy/001.png
evaluation/emotion/test/sad/001.png
evaluation/emotion/test/unknown/001.png
```

```bash
python3 main.py vision --model face --dataset evaluation/face/test --output face-test.json
python3 main.py vision --model emotion --dataset evaluation/emotion/test --output emotion-test.json
```

输出业务准确率和各“实际标签→预测标签”计数，保留逐图数据，方便另算每类召回和误接受率。用于诊断的图片仅保存本地；重新训练时再由团队决定哪些样本上传训练平台。

## 8 是否换平台

推荐短期继续用Edge Impulse，先完成输入一致性、数据拆分与现场测试；它是训练和部署工具，不能替代数据与模型设计。若同样输入在Studio好、EIM差，优先查导出配置与量化；若两边都差，优先查数据、标签和模型。换平台后沿用同一错误数据和裁剪，效果未必改善。

长期若要增加新人员、减少每加一人都重新训练的成本，建议小范围对比“YuNet检测和关键点对齐 + SFace人脸特征 + 本地登记库”。特征向量可以理解为脸的数值描述，通过与登记照片比较识别已知人，并在距离不满足阈值时拒识。OpenCV有对应接口，可先复用已有OpenCV，避免马上引入大型框架。登记库、阈值、陌生人误接受和树莓派耗时都要实测；官网公开数据集成绩不能当成本机准确率。

表情可用OpenCV Zoo的Progressive Teacher模型做第二候选，它采用MobileFaceNet骨干并输出7类可见表情。仍需按实际人脸对齐方式输入，并在同一现场测试集验证；不是直接替换文件名就完成接入。其happy/sad/neutral等标签要明确映射到业务，未知或低置信度不能硬分为二选一。

此前讨论过的OpenFace也可用于对照。它提取面部关键点、头部姿态和AU，即描述脸部肌肉动作的编号；这比只数牙齿白像素更适合分析嘴角和脸颊的变化，但AU仍不是真实心理状态。官方区分静态图像与可做个人校准的视频分析；多人或缺少表情变化时，不能默认校准有效。它需要C++编译器、CMake、OpenCV、OpenBLAS和dlib，当前树莓派ARM64安装、速度尚未验证。推荐先在电脑上验证关键点和AU能否改善同一批失败样本，再决定是否移植；短期不是优先替换整套系统的路线。

| 路线 | 适合用途 | 主要成本 |
| --- | --- | --- |
| Edge Impulse现有分类 | 原五人、已有表情模型快速维护 | 补数据、重训、核对输入和阈值 |
| OpenCV YuNet与SFace | 已知人员登记和扩展身份库 | 检测对齐、登记、相似度阈值与速度测试 |
| OpenCV表情ONNX模型 | 与现有表情模型做独立对照 | 标签映射、对齐和场景验证 |
| OpenFace关键点与AU | 解释可见面部动作，验证微笑判断 | 编译依赖、规则校准、ARM64速度与兼容性 |
| 自训模型加ONNX Runtime | 特定任务需要自定义训练与部署 | 训练代码、版本维护和端侧兼容性 |

不要同时更换相机、裁剪、检测器、模型和平台：先在电脑上用同一批已裁剪测试样本对比分类器，再分别比较检测链路，最后在树莓派测延迟和完整交互。两者都有拒识时同时比较覆盖率与错误率，避免以“少回答”伪装准确率提高。

OpenCV模型版本需匹配。当前YuNet官方同时提供2023固定输入和2026动态输入版本，后者面向OpenCV 5.x的ONNX Runtime引擎；不能不看系统版本就下载最新模型替换。先检查cv2版本和FaceDetectorYN/FaceRecognizerSF接口，使用兼容模型；不要为了试模型盲目覆盖树莓派apt的OpenCV。

本轮没有切换平台、下载替代模型或重新训练，保留现有EIM作为基线。建议选用替代路线的依据是独立测试结果与维护成本，而不是平台宣传或单一公开分数。

## 9 正式新规与后续接口

依据用户提供《陕创赛组〔2026〕7号 人形机器人赛道现场测试的通知》附件3，已核对正文及舞蹈评分表。小人形组每轮5任务、最长8分钟、两轮取最高分，同分比较用时；原始满分210，按比例折算至60。相机支架加入后重新检查厚宽高≤30/30/60厘米、电池≥7.4V。人工干预、脱离场地不能自主返回、摔倒不能自主起身继续会影响对应任务得分。

| 任务 | 正式要求 | 整理版基线与待增加项 |
| --- | --- | --- |
| 园区身份核验30 | 一男一女AI合成脸并标姓名，识别人脸及性别，播报或指定动作 | 原五人分类保留；新任务要独立检测/性别标签识别，是否必读姓名向裁判确认，不能用SFace替代性别任务 |
| 工厂身份核验30 | 原码视觉循迹，通过3个点，每点10 | 原USB扫码和路线解析保留，新增CSI辅助纠偏和实际到点确认 |
| 流水线60 | 三色物块中选指定颜色，搬至指定QR位置 | 固定搬运保留，新增目标颜色、辅助对准、夹持与放置确认；二维码始终原USB读取 |
| 足球30 | 黄色网球、明显踢球、入门投影面，每轮仅一次机会，球不复位 | 固定左脚保留，新增CSI辅助找球/对准、单轮尝试锁定和结果记录 |
| 舞蹈60 | 到区10、音乐舞蹈30、指定语音交互20 | 原舞蹈和口令保留，新增到区与赛前指定交互；表中未到区0分条件须核对分项解释 |

身份任务明确要求人脸及性别，通知还写成功识别但播报未完成或动作错误得5分。姓名打印在图上，但是否必须读姓名、两图如何逐一响应，按裁判公布口径落实。当前原五人识别和happy/sad表情分类都不能直接宣布完成新身份任务。

后续保持三个接口：原视觉任务接主相机；CSI独立提供时间戳、目标偏移、可见夹持状态或地面线偏差，不调用二维码解码器；唯一动作执行者接收任务决策并使用同一个串口。任务插件仍返回成功/失败，必须区分“动作发送成功”和“物体确实到位”。识别错误、丢目标、超时都需停止盲走并返回明确原因。

先原功能回归，再双摄角色接口，再无运动定位显示，再短段纠偏，最后逐项新规任务和整轮。原历史自主寻物代码作为参考，不直接启动其旧协议。起身动作和姿态反馈尚未验证，恢复能力需要单独补齐，不因增加CSI就自然具备。

## 10 常见故障与记录

| 现象 | 优先检查 |
| --- | --- |
| could not open port 0或ttyUSB0 | 用完整/dev/ttyUSB0或完整by-path路径，覆盖错误环境变量 |
| 摄像头初始化失败 | 是否原USB实际视频节点、被其他程序占用、取到metadata节点；源文字发送动作无需相机 |
| RX为空或FB握手超时 | 机器人串口角色、接线、控制板供电及协议状态，不能改成语音模块9600 |
| 人脸框没有出现 | USB画面方向、脸大小、光照、Haar检测；不是先降低身份阈值 |
| 有脸框但认错人 | 裁剪/训练是否一致、完整分数、未知脸误接受、数据泄漏 |
| sad一直unknown | 核对0.95阈值与真实分数、sad样本/标签；不要无测试直接降阈值 |
| 有模型预测但没有声音 | 原录音路径、女声生成、WM8960实际输出、混音音量 |
| 窗口打不开 | 使用Pi桌面会话或正确显示环境，不能将纯SSH窗口错误当模型故障 |

每次记录版本、相机路径/方向、串口路径、真实标签、预测与分数、是否拒识、实际动作、耗时和退出后再次启动结果。软件检查、模拟、单图模型结果与实机整任务结果分别记录。本机检查不能替代树莓派模型推理和现场准确率。
